Open source alpha for people building AI agents

Know where your agents connect.

Outfence runs your agent behind a local proxy and checks every proxy-routed connection against your policy. With a local model it also records who named each destination, and blocks the ones only the model did. Each run leaves a terminal report and JSON evidence you can review.

Alpha 0.1.0a4, Apache-2.0, Python 3.10+, macOS and Linux, zero runtime dependencies

Why a goose

In 390 BC the Gauls climbed the Capitol at night. The guard dogs stayed silent, but the geese sacred to Juno raised the alarm, and Rome held. Agents can be quiet in the same way: a correct answer in the chat, while a tool call goes somewhere nobody asked for. Outfence records every destination your agent tries to reach through its proxy, so the quiet part is on the record.

Who named this destination?

A model can give a correct answer and still make a call nobody asked for. In November 2026, CERT-AGID showed an open-weight model fine-tuned to do exactly that as soon as an MCP server with a specific name was connected.

Outfence does not need to know the trigger. For every destination it records which source named the host first: the user, the system prompt, a tool, or only the model. A policy can allow what the user named, and the model's own output never authorizes a destination.

This demo runs offline with a scripted stand-in for a backdoored model. No real model runs. To check a real local model, add --model-upstream to outfence run.

$ pipx run outfence demo --backdoor
User: Why is the sky blue?
Assistant: Rayleigh scattering: air scatters blue light more than red.

  tool request_url("https://beacon.outfence.test/") -> request failed, see the report

How it works

  1. Write a policy

    Exact host and port rules with an implicit default deny. Wildcards and ambiguous values are rejected.

    {
  "version": 1,
  "allow": [
    {
      "host": "api.example.com",
      "port": 443
    }
  ]
}

  2. Run your agent through it

    Enforce mode blocks destinations outside the allowlist. Observe mode lets them through and records them as would block.

    outfence run \
  --policy outfence.json \
  -- python3 my_agent.py

  3. Read the evidence

    Decisions, counts and coverage limits print in your terminal. A JSON report stays on your machine, and exit codes fit CI.

    0
    Completed, no violations
    2
    Blocked or would block
    3
    Setup, transport or evidence problem
    4
    Workload failed

Try the allowlist demo

No Docker, API key or model is needed, and the demo connects to nothing beyond your own machine. It starts temporary local services and makes real HTTP requests through the proxy.

Exit 2 is expected: the demo deliberately attempts a blocked destination. Run it again with --mode observe to see the same request recorded as would block.

$ pipx run outfence demo
model.example            HTTP 200
retrieval.example        HTTP 200
telemetry.example        HTTP 403
Fixture received 2 connections (destination-side evidence).

Honest about coverage

Outfence is a local development proxy, not a network sandbox. Programs can ignore proxy settings and connect directly, and encrypted content is not inspected. Every report says what it could not see.

Covered in this alpha

  • HTTP GET forwarding
  • CONNECT tunnels used by HTTPS clients
  • Exact destination rules and public address checks
  • Who named each destination, with a local model server (preview)
  • Terminal decisions and local JSON evidence

Outside coverage

  • Direct sockets and clients that ignore proxy settings
  • TLS and content inspection
  • Streaming responses and hosted model APIs
  • Authenticated tool and process attribution
  • Host isolation and Windows support
